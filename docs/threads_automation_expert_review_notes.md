## 검토 배경

- 사용자 제공 텍스트(영상 정리 + 상세 설계안)를 기반으로 문서화된 기능정의의 실현 가능성, 안정성, 정책 리스크를 전문가 관점에서 점검
- Chrome Extension + Codex OAuth Provider Proxy + Ubuntu 서버 + Threads 공식 API를 조합한 구조에서 **운영 리스크와 실행 책임의 경계를 정리**

## 핵심 판단

문서는 전체 운영 루프(수집-분석-작성-승인-발행-학습)를 잘 잡고 있다. 특히 `Companion → Personal Automation → SaaS` 단계 분할은 현실적이다.

다만 실서비스화 관점에서는 다음 항목이 핵심 보완 포인트였다.

1. **예약 발행 책임 분리**
   - Companion 모드가 브라우저 종료 환경에서 자동 발행을 보장하지 못하므로, 자동 발행은 서버 모드로만 허용.

2. **보안 경계 강화**
   - 확장엔 App Secret/장기 토큰을 두지 않는 원칙은 유지.
   - 서버-확장간 교환 토큰은 최소 권한 세션 토큰으로 제한.

3. **중복 발행 방지**
   - 단순 idempotency key 외에 `RUN_AT` 중복 차단 인덱스, Lease 제약, Dead Letter 큐 연동이 필요.

4. **정책 리스크 관리**
   - 자동 좋아요/팔로우/대량 수집/캡차 회피 등은 제외 항목으로 분리해 Web Store·Meta 규정 이슈를 줄임.

5. **Chrome 심사 대응**
   - 권한 사용 목적 설명, 사용자 액션 기반 수집임을 화면/문서로 명시해야 심사 리스크 감소.

6. **운영/운영툴 연동**
   - 토큰 갱신 실패, API 한도 초과, 미디어 URL 만료 같은 장애 시나리오를 문서 단계에서 먼저 설계.
