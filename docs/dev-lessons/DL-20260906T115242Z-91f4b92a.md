# Raw SSE responses must restore validated CORS headers

## 적용 범위와 비적용 조건

Fastify routes that call reply.hijack() and write directly to reply.raw apply. Ordinary Fastify replies that remain under the CORS plugin do not require this extra control.

## 관측 사실과 영향

A real localhost browser completed the generation request but rejected the event stream because the SSE response omitted Access-Control-Allow-Origin. API injection tests and a non-browser HTTP smoke had passed, so the web 1-turn flow ended with Failed to fetch.

## 근본 원인·기여 요인·근거

The SSE handler called reply.hijack() and reply.raw.writeHead(). This bypassed the response-header work normally supplied by the Fastify CORS plugin. The earlier tests asserted status and body but not the CORS header on the hijacked response.

## 해결과 예방 control

For every hijacked SSE response, copy the already validated request origin into Access-Control-Allow-Origin and emit Vary: Origin. Keep the allowed-origin validation before the route and add a regression assertion for the raw response header.

## 검증

The gateway test now asserts the allowed origin on the replayed SSE response. The full test suite passes, and a real Chromium 1-turn run receives all stages, renders the final draft, saves approval, and restores the draft after reload.

## 발생 정보

Observed during the 2026-09-06 localhost web 1-turn acceptance test after the initial web-first implementation. Impact was limited to the new web surface and no post was published.

## 검토와 예외

Recheck this control when changing Fastify, the CORS plugin, SSE transport, or any direct Node response handling. No exception is currently approved.
