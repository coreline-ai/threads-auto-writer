## 개발 목적

Threads 웹페이지에서 사용자가 선택한 참고 글을 기반으로, `Codex OAuth Provider Proxy`가 구조 분석·다중 후보 생성·비평·최종 개선·위험 검수를 수행하고, 사용자가 승인한 글을 Threads 기본 작성·예약 UI로 전달하는 `ThreadFlow OS`를 개발한다.

MVP의 성공 기준은 게시 자동화의 양이 아니라 다음 세 가지다.

- 참고 글을 베끼지 않으면서 독창적인 최종 글을 만든다.
- Persona와 게시 목적에 맞는 품질을 반복적으로 재현한다.
- OAuth 자격 증명과 사용자 초안을 안전하게 다룬다.

## 문서 기반 제약 사항

- 제품 내부에 글당·일일 토큰 제한을 구현하지 않는다.
- 서비스의 일시적인 401·429·5xx와 Rate Limit 상태는 안정성 오류로 처리한다.
- 모델 ID를 UI와 비즈니스 로직에 하드코딩하지 않고 Proxy의 승인된 기본값을 사용한다.
- Codex OAuth Access/Refresh Token은 Codex App Server가 소유하며 Extension·IndexedDB·ThreadFlow Scheduler·애플리케이션 로그에 복사하지 않는다. Threads User Access Token은 공식 API 자동 게시 시에만 Scheduler Vault에 암호화 저장한다.
- 원문과 생성문은 기본 로그에서 제외하고 Prompt 버전·모델·지연 시간·점수·오류 코드만 기록한다.
- Threads 원문은 구조 분석 자료이며 문장 치환형 재작성의 원본으로 사용하지 않는다.
- 숫자·가격·날짜·효능·수익 주장은 사용자 근거가 없으면 `REVIEW_REQUIRED`로 처리한다.
- 사용자의 최종 승인 없이는 게시·예약·댓글·좋아요·팔로우를 실행하지 않는다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 요구사항이 불명확하면 가능한 케이스를 나누고 확인 후 진행한다.
- 한 기능은 유지보수 가능한 최소 책임 단위로 나누고, 각 단위의 역할과 경계를 계획에 적는다.
- 계획 밖 옵션·확장·부가 기능을 만들기 위한 분리는 하지 않는다.
- 공통화는 계획 범위 안의 중복을 줄일 때만 수행하고 과도한 추상화는 피한다.
- 기존 프로젝트 API, 공식 SDK, 표준 라이브러리를 우선 검토하고 새 의존성은 범위상 필요할 때만 포함한다.
- 각 Phase 완료 시 구현 변경, 테스트 결과, 남은 위험을 현재 문서에 기록한다.
- Live OAuth·Threads 로그인 테스트는 명시적 opt-in smoke test로 분리하고 CI에 자격 증명을 넣지 않는다.
- 외부 페이지와 모델 출력은 신뢰할 수 없는 입력으로 취급한다.

## 잔여 리스크 / 후속 과제

- Codex App Server와 ChatGPT 구독의 실제 가용 모델·일시적 사용 제한은 실행 시점 계정 상태에 의존한다. 앱 내부 글당·일일 Token 상한은 두지 않는다.
- Threads 작성창 DOM은 변경될 수 있으므로 클립보드 fallback을 유지하고 실제 계정 회귀 Smoke가 필요하다.
- Companion 설치물은 생성됐지만 공개 배포 전 macOS Developer ID 서명·공증이 필요하다.
- LLM 품질 점수는 절대 지표가 아니므로 실제 사용자 편집량과 사람 평가를 함께 추적해야 한다.
- 공식 Threads API 자동 게시·Insights는 Meta App 심사와 실제 계정 검증 전 운영 활성화하지 않는다.
- 다계정 코드 경계는 구현됐지만 외부 IdP·결제·운영 승인은 별도 제품 정책이 필요하다.
